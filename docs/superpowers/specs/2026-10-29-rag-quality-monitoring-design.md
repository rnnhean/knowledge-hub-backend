# RAG 质量监控设计（线上层）

- 日期：2026-10-29
- 项目：knowledge-hub-backend
- 状态：设计稿
- 前置阅读：[docs/CC-FROM-ZERO.md](../../CC-FROM-ZERO.md) 第十章（离线评测的建立与纪律）

> 现状描述已对照源码核对（2026-10-29）；标注为计划的项尚未实现。

---

## 1. 为什么需要这份文档

项目已经有一套完整的**离线评测**：金标集、9 个评测器、Langfuse Experiment。它回答的是「我这次改动有没有让效果变差」。

但它回答不了另一个问题：**「线上现在好不好」**。

两者不是同一件事：

| | 离线评测（已有） | 线上质量监控（本文档） |
|---|---|---|
| 触发方式 | 手动 `pnpm eval:rag` | 持续采集 + 定时聚合 |
| 数据来源 | 固定金标集（人工出题） | 真实用户流量 |
| 能测的指标 | 需要标准答案的（Hit@5、Precision、完整度、意图） | 无参考指标（忠实度）+ 代理信号 |
| 目的 | 防止改动导致退化 | 发现线上真实退化 |
| 与发布的关系 | 不阻断 PR（见 CC-FROM-ZERO 第十章纪律） | 触发告警，不阻断发布 |

**关键认知**：金标集永远覆盖不到真实用户的长尾问题。离线全绿，不代表线上没问题。反过来，线上指标波动，也不一定说明代码改坏了——所以两套必须分开建、分开看。

## 2. 目标与非目标

### Goals

1. 回答维度有用户反馈入口（👍/👎），并能关联到对应的 Langfuse trace
2. 采集并聚合 6 个线上代理指标，能按天看趋势
3. 按比例抽样跑无参考指标（忠实度），结果落 Langfuse
4. 低分样本可导出，人工确认后回流金标集
5. 关键指标异常时可告警

### Non-goals

- **不替换**离线评测，也不改变 CC-FROM-ZERO 第十章的评测纪律
- 不做实时（秒级）监控，按天/按小时聚合即可
- 不对每一条线上回答都跑 LLM judge（成本不可控）
- 不做自动修复（如自动调整检索参数）

### Anti-goals

- **用代理指标冒充准确率**：拒答率高不等于准确率低，没验证相关性之前不能直接当质量分
- **judge 打分不校准**：LLM-as-judge 本身会漂移，不校准就是在监控 judge 而不是监控系统
- **把抽样 judge 做成同步阻塞**：不能拖慢 SSE 响应

## 3. 指标分层：哪些能线上化

RAG 质量必须拆三层，因为线上能拿到的信号完全不同：

| 层 | 离线指标（已有） | 线上可测 | 说明 |
|---|---|---|---|
| **检索层** | `hit_at_5`、`precision_at_5` | ❌ 不可直接测 | 需要标准答案，线上没有 |
| | | ✅ 空召回率、改写重试率 | 代理信号，需验证相关性 |
| **生成层** | `completeness`、`groundedness` | ⚠️ 只能跑 `groundedness` | 忠实度不需要金标，只需「回答 + 检索资料」 |
| | `refusal_quality` | ⚠️ 拒答率需另写规则判定——`refusal_quality` 依赖金标 `expectRefusal`，线上无金标时恒返回 `null` | 拒答内容可用 judge 抽样确认 |
| **端到端** | — | ✅ 用户反馈、追问率 | 唯一真值信号，但稀疏 |

**结论**：线上监控的重心是「生成层 + 端到端」，检索层只能靠代理信号。

## 4. 三类线上信号

### 4.1 真值信号：回答级用户反馈

这是唯一能直接知道「答得好不好」的渠道，优先级最高。

**前端**：

- 在每条助手回答下方加 👍 / 👎
- 现有 `DocumentEngagement` 是文档维度的点赞/收藏，**不复用**，另建回答维度的反馈组件
- 👎 可选填原因：`与问题无关` / `内容不准确` / `信息不完整` / `其他`
- 反馈只在流式回答结束后展示

**后端**：

- 新增接口接收反馈，入参必须包含能定位 trace 的信息：`sessionId` + `messageId`（或 Langfuse `traceId`）
- 通过 Langfuse API 给对应 trace 写 score：`{ name: 'user_feedback', value: 1 | 0, comment: reason }`
- 当前 SSE 链路需要确认 trace id 是否回传到前端；若没有，需在流结束事件里带上

**已知局限**：反馈率通常只有 1%–5%，且以负面反馈为主（满意的人不点）。所以它适合「发现问题样本」，不适合「算准确率」。

### 4.2 代理信号（密集，需验证相关性）

这些不需要用户操作。但注意：当前线上链路不产出 `ChatEvalSnapshot`（该快照只在评测入口 `runForEval` 里组装），SSE 只推 `retrieveEval`；要做到直接统计，需先在 `streamChat` 与落库环节补齐快照。

| 信号 | 数据来源 | 计算方式 | 突增含义 |
|---|---|---|---|
| **空召回率** | `rawHits.length === 0` 或 `retrieveEval.reason` 以 `empty` 开头（`gradedHits` 是切题过滤后的结果，不能用来判空召回） | 空召回请求数 / 总请求数 | 检索变差或文档覆盖不足 |
| **改写重试率** | `retrieveEval.retried` | 重试请求数 / 触发检索的请求数 | 首轮召回质量下降 |
| **拒答率** | 回答内容判定（需另写规则判定；`refusal_quality` 有金标门禁，线上直接调用只会返回 `null`） | 拒答数 / 总回答数 | 检索或覆盖问题 |
| **追问率** | 同会话内连续提问 | 发生追问的会话数 / 总会话数 | 上一轮没答好 |
| **引用点击率** | 前端点击 `[1] [2]` 的事件 | 点击次数 / 有引用的回答数 | 低：不信任引用或不相关 |
| **会话放弃率** | 问一句后无后续且很快离开 | 放弃会话 / 总会话 | 答非所问 |

**聚合维度**：按天 × intent（chitchat / profile / kb / web / kb_then_web）× 领域（suites）。只按全局看会被闲聊题稀释。

**必须先做的一步：验证相关性**。M1 上线并积累 👎 样本后再做相关性回测（当前系统无反馈功能，现有样本为 0）——如果 👎 样本的空召回率、追问率显著高于 👍 样本，说明代理指标有效；如果没有差异，就不要把它当质量指标用。

### 4.3 抽样 judge（平衡成本与覆盖）

- **抽样率**：5%（可配置），按 `sessionId` 哈希保证同一会话稳定在同一组
- **只跑无参考指标**：`groundedness`（复用 [evaluators.ts](../../../src/ai/eval/evaluators.ts) 已有实现）
- **执行方式**：异步，在流结束后投递到队列（可复用 `src/mq/` 的 publish 封装，但需新增 judge/quality 的交换机与队列——当前仅有 `rag.reindex` / `search.index` / `kg.graph` 三组），不阻塞响应
- **结果写入**：Langfuse score，`{ name: 'sampled_groundedness', value: 0 | 0.5 | 1 }`
- **成本控制**：只对本轮有 `gradedHits` 的回答抽样；纯闲聊题跳过

### 4.4 离线定时回归（补充，不改纪律）

- **（M4 计划）** 每日定时跑一次 `run-experiment.ts`（cron / 本地计划任务），存基线——当前无调度器依赖、`run-experiment` 也不落盘基线，需一并补齐
- **不进 PR CI**，不阻断合并——遵守 CC-FROM-ZERO 第十章的纪律
- 对比对象是「昨天 vs 今天」，不是「本次 PR vs 主干」
- 分数下降超过阈值时通知，由人判断是模型随机性还是真退化

## 5. 闭环：低分样本回流金标集

这是让监控产生长期价值的关键环节，没有它，监控只是发现问题。

```
线上流量
  ├─ 👎 反馈
  ├─ 抽样 groundedness < 0.5
  └─ 代理指标异常时段的样本
        ↓
   人工复核（每周一次）
        ↓
   确认为真实错误的 → 补进 golden-dataset.ts
        ↓
   跑一次离线评测，更新基线
```

**纪律**：

- 补进金标集的题目必须人工确认过，不能把模型判错的直接当金标（judge 也会错）
- 每题要能标注出处的文档依据
- 新样本加入后，历史基线需要重跑，否则新旧基线不可比

## 6. 报警设计

与前端监控的报警分开——这里报的是「质量信号」，不是「系统错误」。

| 规则 | 条件 | 级别 |
|---|---|---|
| 抽样忠实度下降 | 7 日滚动均值较上周下降 > 10% | P1 |
| 追问率突增 | 日追问率 > 前 7 日均值 × 1.5 | P1 |
| 空召回率突增 | 日空召回率 > 前 7 日均值 × 1.5 | P2 |
| 👎 率突增 | 日 👎 率 > 前 7 日均值 × 2 | P2 |
| 拒答率突增 | 日拒答率 > 前 7 日均值 × 1.5 | P2 |

**降噪**：

- 用 7 日滚动均值做基线，避免单日波动误报
- 只在连续 2 天超过阈值时告警
- 发版当天不告警（等待流量稳定）

## 7. 落地顺序

| 阶段 | 内容 | 依赖 | 预计 |
|---|---|---|---|
| **M0 数据打通** | 确认 SSE 流结束事件能回传 `traceId` / `messageId` | 无 | 0.5 天 |
| **M1 反馈闭环** | 前端 👍/👎 + 后端写 Langfuse score | M0 | 1 天 |
| **M2 代理指标** | 落一张 `chat_quality_daily` 聚合表（或打 Langfuse），按天聚合 6 个信号 | 需新增：线上产出并落库 `ChatEvalSnapshot` | 1 天 |
| **M3 抽样 judge** | 队列异步跑 `groundedness`，写 score | M0 | 1 天 |
| **M4 报表与告警** | 简单看板（SQL / Langfuse Dashboard）+ 规则 | M1–M3 | 1 天 |
| **M5 回流机制** | 每周导出低分样本，人工复核，补金标集 | M1–M3 | 持续 |

**M2 可以先做**：它不依赖任何前端改动，纯后端聚合，能最快看到趋势。

## 8. 验收标准

**M1**

- [ ] 一次问答结束后点 👎，Langfuse 中对应 trace 出现 `user_feedback=0`
- [ ] 反馈能追溯到具体会话与消息
- [ ] 反馈接口不会因为 Langfuse 未配置而报错（降级为本地日志）

**M2**

- [ ] 连续跑 10 次问答（含空召回、改写重试场景），聚合表数据与手工核对一致
- [ ] 能按 intent 分组查看

**M3**

- [ ] 抽样率 5% 生效，同会话稳定
- [ ] judge 失败不影响主流程
- [ ] 抽样成本可估算（每天约多少次 judge 调用）

**M4**

- [ ] 制造一次空召回率突增，能触发告警

## 9. 风险与待定项

| 项 | 说明 | 处置 |
|---|---|---|
| **反馈稀疏** | 反馈率 1%–5%，且以负面为主 | 不拿反馈算准确率，只用来发现问题样本 |
| **代理指标相关性未验证** | 拒答率高可能是用户问得超纲 | M1 上线并积累 👎 样本后再回测（当前无反馈功能、样本为 0），无区分度就不采用 |
| **judge 漂移** | judge 模型更新或 prompt 调整会导致分数变化 | 每季度用 50 条人工标注算一致率，低于 80% 就重校准 |
| **抽样成本** | 5% 抽样 × 日均问答量 × judge token | 只对有检索结果的回答抽样；设置日上限 |
| **数据隐私** | 抽样 judge 会把回答与检索片段送给 LLM | 与现有 RAG 链路同一供应商，不新增出域；如需更严，抽样时脱敏文档标题 |
| **`ChatEvalSnapshot` 线上是否可用** | `includeEval` 目前只是 service 内部选项，`ChatDto` 与 controller 均未透传，HTTP 层无法开启，需先补 DTO 与参数透传 | SSE 场景需确认能否拿到 `retrieveEval` / `gradedHits`；拿不到则改为在服务端落库 |
