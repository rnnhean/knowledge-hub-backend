# 用 Claude Code 从零到一实现 knowledge-hub

> **这份手册的前提是：目录是空的。**
> 下文每一段提示词，粘出去时你手上没有一行代码。
> 文中出现的文件路径、字段名、接口路径，是**你要让 AI 产出它们**，不是让它去读。
>
> 唯一的例外是最后一章：那里才讲这个成品后来长成了什么样，作为参照，不构成施工输入。

---

## 零、先接受三个事实

### 事实一：写代码是从零到一里最不重要的部分

真正决定成败的是三个决策，**都必须你拍板，AI 只能帮你想**：

1. **MVP 的范围**——含不含审核流？含不含知识图谱？含不含多人协作？
2. **一致性边界**——哪些写入必须事务，哪些可以异步重试？不一致时用户看到什么？
3. **第一条竖线的验收命令**——跑不出来就不许进第二条

这三件事定的越早，后面代码的形状越稳。定不下来就开工，结果一定是返工。

### 事实二：一次会话只推一条竖线

"帮我做一个企业知识库系统"这个提示词，得到的一定是能跑 demo 但每层都薄的骨架——**因为没有一条竖线被真正打通过**。

正确粒度是一次会话一条竖线，且这条竖线有能跑的命令级验收。

### 事实三：AI 会把没验证的说成验证过

这是这套流程真正的敌人。所以每条提示词都必须包含**验收命令**和**停止点**，并且写死一句：

> 没跑通就直接说没跑通，禁止用"应该可以"、"理论上"、"已实现"。

## 一、开工前：把需求逼成边界（这一步不写代码）

从零第一天，你手上只有一句话需求。直接让 AI 写代码，它会在你没想清楚的地方替你做了决定——而你根本不知道它决定了什么。

### 提示词 1-0-A（逼边界）

```
我要做一个企业知识库系统，现在目录是空的。

先不要写代码，不要问我想用什么框架，不要输出架构图。

需求原话：员工上传公司制度 PDF，用自然语言提问，
系统基于文档回答并给出引用；查不到就说查不到，不许编。

你的任务是把这句话逼成一份可验收的规格，输出三部分：

【1】这个需求里最容易做偏的三处，以及为什么
     我要的是你能看出的坑，不是教科书条目。
     每一条说清楚：做偏了会表现成什么样，怎么才能早点发现。

【2】为了能验收，还需要我回答哪些问题。
     最多 8 个，每个给两个候选答案让我选，不要开放式提问。

【3】最小可交付版本包含什么、明确不包含什么。

我要的是边界，不是方案。
```

**为什么第 2 条要"给两个候选答案"**：开放式提问会把你拖进无穷讨论；选择题十分钟就能收敛。

### 提示词 1-0-B（锁定范围）

```
基于我选定的答案，把 MVP 范围写成一份清单，存成 docs/SCOPE.md。

格式：
## 做
- 每条一句话，可验收

## 不做
- 每条写清楚"为什么现在不做"，以及"以后要加时会影响哪些地方"

## 明确不做但容易被误解为要做的
- 例如：多人实时协同编辑、移动端 App、多租户

约束：不做清单至少 8 条。做得少不是缺点，边界不清才是。
写完停下，等我确认。
```

**这一步的产出物是 `docs/SCOPE.md`**，后面每次会话都让它先读这个文件。

## 二、数据模型：先证明 Postgres 够用

新手最容易犯的错：一开始就把 ES、向量库、图数据库全架上。**一堆中间件同时起，任何一环出问题都定位不了。**

### 提示词 2-A（数据模型，仍不写业务代码）

```
基于 docs/SCOPE.md，产出数据模型。仍然不写业务代码。

要求：
1. 列出所有实体和字段，每个实体旁边写一句「谁会读它」。
   读不出使用场景的实体，直接删掉，不要留"以后可能有用"的
2. 标注每个实体：强一致（必须事务）还是可以最终一致
3. 明确回答：文档正文和元数据分别存在哪、为什么分开
4. 画出两条数据流，每条标出失败时的补偿手段：
   - 发布一篇文档
   - 用户提问一次
5. 给出建表 SQL，存成 docs/schema.sql

硬约束：
- 不要引入 Elasticsearch / 向量库 / 图数据库 / 消息队列。
  先证明只用 Postgres 能跑通最小版本
- 如果某处确实做不到，说明「为什么 Postgres 做不到」，
  而不是直接换成新组件
- 主键用雪花 ID 而不是自增，理由是后面会分片；如果你有别的看法先说

产出 docs/DATA-MODEL.md 和 docs/schema.sql，写完停下。
```

**这条硬约束是本手册最重要的设计。** 你现在看到的成品用了 6 个中间件（外加主库 Postgres），但那是**到了第 5 条竖线才逐个加进来的**。第一版只用 Postgres，能跑通"上传→提问→回答"，才有资格讨论要不要加别的。

### 2-B：什么时候才允许加中间件

每加一个，都要能回答这三个问题，答不上来就别加：

| 问题 | 答不上来的后果 |
|---|---|
| 现在用 Postgres 的什么实现，慢在哪/差在哪 | 你会为了"看起来专业"而加组件 |
| 加了之后，哪条数据变成了两份 | 后面必然出现一致性问题 |
| 这一份挂了，用户看到什么 | 挂了就是白屏或者数据错乱 |

本成品后来加中间件的顺序，可以作为参照（**但不是让你一次全上**）：

| 什么时候 | 加了什么 | 为了什么 |
|---|---|---|
| 检索质量不够时 | Elasticsearch + IK 分词 | 中文全文检索 |
| 要做语义检索时 | pgvector（**注意是 Postgres 扩展，不是独立组件**） | 向量检索 |
| 发布后要跑重活时 | RabbitMQ | 异步管线，避免请求阻塞 |
| 要做实体关系时 | Neo4j | 知识图谱 |
| 要存大正文和图片时 | 对象存储（S3 兼容） | 大字段不要塞数据库 |
| 要缓存和验证码时 | Redis | 会话、限流 |

注意 pgvector 这一行：它是 Postgres 扩展，**没有引入新组件**，符合"先证明 Postgres 够用"的原则。

## 二·五、技术栈选型：怎么选，以及每个选择的代价

选型是最早做、最难改的决策。这一节不讲"各语言优劣"，只讲**在这个项目里，每个选择分别付出了什么代价**。

### 2.5.1 选型的正确顺序：从约束出发，不是从技术出发

不要问"Node 和 Java 哪个好"，要问下面这五个问题，答案会自己指向技术栈：

| 问题 | 这个项目的回答 | 指向 |
|---|---|---|
| 核心路径是 I/O 密集还是 CPU 密集？ | 提问/检索/流式回答 = **纯 I/O 密集**；解析 = CPU 密集但低频 | Node 可用，但解析要隔离 |
| 前后端是否大量共享类型/枚举/契约？ | 是。8 种 data part、权限点、状态枚举 | 同语言收益大 |
| 有没有特定生态只有某语言有？ | AI SDK（`ai` + `@ai-sdk/react`）在 TS | Node 收益大 |
| 团队规模和背景？ | 前端转全栈，一个人 | Node 上手成本最低 |
| 峰值并发量级？ | 企业内部系统，日活百级 | 还没到需要 Go/Java 的级别 |

**五个问题里四个指向 Node，唯一指向别的（CPU 密集）可以通过工程手段规避。** 这就是选型的答案。

### 2.5.2 前端选型：为什么是 React + Ant Design，不是 Vue + Element

| 维度 | 选择 | 代价 / 理由 |
|---|---|---|
| 框架 | React 19 | AI SDK 的 `useChat` 只官方支持 React——**这条基本决定了框架** |
| 组件库 | Ant Design 6 | 管理端表格/表单/弹窗是主场景，antd 开箱即用；代价是**包体积大**（首屏 gzip 后仍不小），且定制样式要跟 CSS-in-JS 打架 |
| 路由 | React Router 7 | 24 条路由，含权限包裹的嵌套路由；没用 Next.js 是因为**不需要 SSR**（内部系统，SEO 无意义，多一层构建更麻烦） |
| 样式 | 手写 CSS 1270 行 | 没用 Tailwind。代价是**样式散落**；优点是没有构建链依赖。这个规模（19 个页面）还能撑住，再多就该上方案了 |
| 图表 | ECharts | 知识图谱的力导向布局，ECharts 的 `graph` + `force` 是最省事的；代价是**包大**，且要手动处理"渲染完成才能导出图片" |
| 数据获取 | **没有** TanStack Query / SWR | 这是最大的技术债之一，见下 |

**关于数据获取，必须说实话**：仓库里每个页面都是 `useEffect` + `useState` 手写：

```ts
// DocumentsPage.tsx:55 附近
useEffect(() => { load(); }, []);
```

代价很具体：
- 没有缓存，切页面回来重新请求
- 没有请求去重，同一份数据多个组件各拉一次
- 没有重试、没有乐观更新、没有失效策略
- 每个页面重复写 loading / error 状态

**一旦超过 10 个页面，这套手写方式就开始失控**。如果从零做，我会在第 5 个页面时引入 TanStack Query，它不是"锦上添花"，是把 requests 的管理从每个组件收回到一个地方。

> 判断标准：当你开始第 3 次复制 `useEffect(() => { load() }, [])` 时，就该引入了。

### 2.5.3 后端选型：为什么是 Node

#### 好在哪（这个项目里能验证的）

**1. 契约能共享，改一处两边一起报错**

前后端 2 万多行 TS。后端的 `ChatStreamDto` 字段、前端 `KhUIMessage` 类型、权限点枚举、文档状态码——**同一个定义两边引**。跨语言方案里这些全靠手抄，漏一处就是线上 bug。

**2. I/O 密集正好对路**

一次问答要并发调检索 + 图谱 + 改写，全是"等外部服务"。Node 的单线程事件循环处理这种场景不用管锁，也不会因一个慢查询占满线程池。

**3. 流式转发是主场**

Node Stream 的背压机制让 LLM token 流能原样透传给前端，中间不攒。这是这个项目核心体验的技术底座。

**4. AI SDK 生态在 TS**

`ai` + `@ai-sdk/react` 同一套协议，前后端 data part 天然对得上。换语言要么自己实现协议，要么用非官方 SDK。

#### 不好在哪（这个项目里已经暴露的）

**1. CPU 密集是死穴，而项目恰好有**

解析器用了 `pdf-parse`（内含 wasm）、`mammoth`、`jszip`——都是同步计算。而上传接口是**同步解析**：

```ts
// document.service.ts:584
parsedContent = await this.fileParserService.parse({ ... });  // 请求线程里直接解析
```

一份 50MB 的 PDF 解析十几秒，这期间**整个事件循环被占住**——不是那个请求慢，是所有人的所有请求都慢。

> 实际情况：`src/` 里没有任何 `worker_threads` / `child_process`。**没做线程隔离**，这是最该补的性能隐患。

**2. 雪花 ID 精度坑，已经踩了**

```ts
// document.entity.ts
@PrimaryColumn({ type: 'bigint', transformer: bigintTransformer })
id: string;
```

19 位雪花 ID 超过 JS `Number` 的安全整数上限（2^53-1）。**不转字符串不报错，但 ID 会静默变成另一个数**。靠一个 `bigintTransformer` 兜住，意味着每个碰 bigint 的地方都不能忘。Go/Java 没这个问题。

**3. 类型只活到编译期**

TS 的 interface 编译完就没了。运行时校验全靠 `class-validator` 装饰器，**漏写一个字段就是未校验入参**。Java 至少反射还能兜底。

**4. MQ 消费没有并发控制**

```ts
// rabbitmq.service.ts:200
await ch.consume(queue, async (msg) => { ... });   // 没有 prefetch
```

MQ 里堆 100 条消息会全部推给这个进程并发执行——**并发启动是廉价的，昂贵的是后面那段**，结果把 API 请求饿死。这是 Node 特有的坑。

#### 为什么最后还是选 Node：算的是这笔账

| 项目特征 | 谁吃亏 | 权重 |
|---|---|---|
| 契约高度耦合（8 种 part + 权限点 + 状态枚举） | 跨语言方案 | 高 |
| 流式问答是核心体验 | 非 Node 要额外对齐协议 | 高 |
| AI SDK 生态在 TS | 其他语言得自己补 | 中高 |
| 解析是 CPU 密集 | Node 天然吃亏 | 中（但低频） |
| 并发量级 | 企业内部，日活百级 | 低 |

**关键判断在第四行**：CPU 密集虽然是 Node 的短板，但**不是高并发场景**——一天几十份文档，不是一个小时几十份。风险是"有概率发作"，不是"持续拖累"。

而核心路径（提问、检索、流式回答）是纯 I/O 密集，恰好是 Node 最强的部分。**用低频场景的短板，换高频场景的长板，这笔账是划算的。**

#### 如果重来，我会怎么补（不是换语言）

**补丁一：解析丢进独立进程**

```
上传接口改成「只存文件 + 发 MQ」，解析交给 worker_threads 或独立解析服务。

验收：
1. 上传一个 50MB PDF，期间**同时**请求健康检查接口，
   响应时间必须仍在 100ms 内（证明事件循环没被占）
2. 解析失败不影响上传接口返回
3. 解析进度可查（前端轮询状态字段）
```

**补丁二：给消费端加 prefetch**

```
给 MQ 消费者设 prefetch(1~2)。

理由：不设的话，队列里 100 条消息会全部推给进程并发跑，
抢占事件循环，把 API 请求饿死。

验收：
1. 一次发布 50 篇文档，制造 50 条消息
2. 期间持续请求健康检查，响应时间必须平稳
3. 观察日志：同时在跑的消费任务数不超过 prefetch 值
```

**这两条都不需要换技术栈——说明选型本身没错，是使用方式没跟上。**

#### 什么情况下我会改选别的

| 场景 | 换成 | 换来什么 / 失去什么 |
|---|---|---|
| 解析成为核心瓶颈（日均万份） | 解析服务用 Go/Python，Node 只做网关 | 换来 CPU 隔离；失去单体部署的简单 |
| 需要自己跑 embedding / 大量数值计算 | Python | 换来生态；但用户明确不碰模型训练，**不适用** |
| 团队全是 Java 背景、且不需要前端复用 | Java / Kotlin | 换来稳定性；失去契约共享 |

### 2.5.4 选型自检提示词

开工前用这段把选型问清楚，写进 `docs/ADR-001.md`：

```
在设计数据模型之前，先把技术选型定下来，输出 docs/ADR-001.md。

先回答这五个问题（不要跳）：
1. 核心路径是 I/O 密集还是 CPU 密集？各自占比多少、调用频率多少？
2. 前后端需要共享哪些类型/枚举/契约？列出来
3. 有没有哪个功能只有特定生态能做？列出来
4. 峰值并发量级是多少？给出估算依据
5. 团队背景是什么？

然后给结论，每个选型必须同时写「收益」和「代价」两栏：

| 层 | 选择 | 收益 | 代价 | 什么情况下会后悔 |
|---|---|---|---|---|
| 前端框架 | ? | | | |
| 组件库 | ? | | | |
| 前端数据获取 | ? | | | |
| 后端语言/框架 | ? | | | |
| ORM | ? | | | |
| 数据库 | ? | | | |

硬要求：
- 「代价」一栏不许写"无明显缺点"。每个选择都有代价，
  写不出来说明你没想清楚
- 「什么情况下会后悔」必须具体到可观测的指标
  （例如：单表超过 500 万行 / 上传队列积压超过 100）
- 不要引入当前不需要的东西。每引入一个组件，
  回答：现在用什么替代、替代方案的瓶颈在哪、这个组件挂了用户看到什么

写完停下，等我逐条确认。
```

**这张表里"什么情况下会后悔"那一列最重要。** 选型本身很难一次做对，但只要你提前写明了"什么信号出现时说明该换"，就不会一路将错就错。

### 2.5.5 本成品的技术栈与真实代价汇总

| 层 | 选了什么 | 真实代价（实测/代码可见） |
|---|---|---|
| 前端框架 | React 19 | AI SDK 的 `useChat` 只支持 React——**这是被动选择** |
| 组件库 | Ant Design 6 | 包体积大；深度定制要跟 CSS-in-JS 打架 |
| 路由 | React Router 7 | 无 SSR，首屏全是客户端渲染 |
| 样式 | 手写 CSS 1270 行 | 样式散落，无作用域隔离 |
| 数据获取 | 手写 `useEffect` | **无缓存 / 无去重 / 无重试**，页面多了会失控 |
| 图表 | ECharts | 包大；导出图片要等渲染完成 |
| 后端框架 | NestJS 11 | 装饰器 + 依赖注入，学习成本高于 Express，但结构清楚 |
| 语言运行时 | Node 20 | **解析阻塞事件循环**（未隔离）；bigint 精度坑 |
| ORM | TypeORM | 迁移要手配；`synchronize` 必须关 |
| 主库 | PostgreSQL | 19 张表存元数据与权限；**没有用它做向量检索** |
| 全文检索 | ES + IK | **正文存两份**（Mongo + ES），一致性成本高 |
| 向量 | ES `dense_vector` | 1024 维 cosine，和关键词检索共用同一索引；ES 的容量与运维成本被放大 |
| 图 | Neo4j | 三套索引的一致性维护成本 |
| 消息队列 | RabbitMQ | **消费端未设 prefetch**，有并发失控风险 |
| 缓存 | Redis | — |
| 对象存储 | S3 兼容 | — |
| AI | Vercel AI SDK | 版本迭代快，API 有 breaking change |

**看这张表的方式**：不要看"选了什么"，看"代价"那一列——**每一个代价都是可以提前设计掉的**，而它们全都没被设计掉，是因为当时只想快点看到效果。

## 三、第 0 条竖线：让它能起来

### 提示词 3-A（骨架 + 健康检查）

```
搭后端骨架。此时只有 docs/schema.sql，没有业务逻辑。

技术选型：见 docs/ADR-001.md（上一节 2.5.4 的产出）。
本文默认 NestJS + TypeScript + TypeORM + Postgres，
如果你 ADR 里选了别的，以 ADR 为准。

要求：
1. 分层目录：src/{模块}/{controller,service,entity,dto}
```

## 四、第 1 条竖线：鉴权

鉴权必须先于业务。理由很实际：**后面每个接口都要鉴权，晚做就要回头改所有接口。**

### 提示词 4-A（设计先行）

```
设计鉴权方案，先不写实现，输出到 docs/AUTH-DESIGN.md。

必须回答：
1. access token 和 refresh token 各自多长有效期，为什么
2. token 存在前端哪里（localStorage / cookie / 内存），
   每种选择被 XSS 和 CSRF 攻击时分别会怎样
3. 并发请求同时遇到 401 时，是每个都去刷新，还是共享一次刷新？
   共享的话怎么实现（提示：single-flight）
4. 权限模型：角色 + 权限点，还是只有角色？说清楚以后加一个
   「只能看自己团队的文档」这种规则时，模型撑不撑得住
5. 登出时怎么做才真的让 token 失效（JWT 无状态，直接删前端不够）

每条给一个推荐答案 + 一句反对意见。
写完停下，等我拍板。
```

**第 5 条是很多人栽的地方**：JWT 删了前端的 token 不等于 token 失效，服务端仍认它。要么用短有效期 + refresh 撤回，要么维护黑名单。

### 提示词 4-B（实现）

```
按 docs/AUTH-DESIGN.md 实现鉴权竖线。

范围严格限定：
- 后端：注册、登录、refresh、登出、GET /auth/me
- 前端：登录页、token 存取、请求层（带 token + 401 自动刷新）

后端要求：
- 密码 bcrypt 哈希，禁止明文，也禁止在日志里打印
- 全局守卫默认要求登录，用 @Public() 放行例外
- 守卫执行顺序：先认证（是谁），再授权（能不能做）

前端要求（这条最容易做错，重点）：
- token 存 localStorage
- 401 时用 single-flight 刷新：并发多个请求共享同一个 refresh Promise，
  刷新成功只重试一次，失败统一跳登录
- 不能每个请求各刷一次，会把 refresh token 打爆

验收（对着浏览器真看，不是看代码）：
1. 注册 → 登录 → 拿到两个 token
2. 不带 token 请求 /auth/me → 401
3. 带 token 请求 → 200
4. 刷新页面仍保持登录
5. 【关键】手动把 localStorage 里的 access token 改坏，触发一次请求，
   打开 Network 面板，应该看到：
   401 → 一个 refresh 请求 → 原请求重试 → 成功
6. 【关键】同时点三个需要鉴权的按钮，Network 里 refresh 只出现一次

第 5、6 条做不到就是 single-flight 没写对。不要跳过，不要改验收标准。
```

**第 6 条为什么必须测**：单飞刷新最容易写出"看起来对但并发会炸"的版本。看 Network 面板比让它自述"已实现"可靠一百倍。

```
第 5 条如果没过，说明需要更好的中文分词——这时候才有理由考虑 ES。
```

### 提示词 7-B（向量检索，仍然不引新组件）

```
加语义检索能力。第一版可以用 pgvector（Postgres 扩展，不引入独立向量库）。
**成品最终没有走这条路**：向量放进了 ES 的 dense_vector，因为关键词与向量要共用同一套权限过滤条件，放在一个索引里少一次查询；代价是 ES 的容量与运维成本被放大。

理由：语义检索现在只需要一个扩展就够，独立向量库是数据量到百万级之后才需要。

要求：
1. 建 embedding 表和索引（HNSW 或 IVFFlat，说明你怎么选）
2. 分块后调 embedding 服务写入向量
3. 检索时向量召回 + 关键词召回，用 RRF 粗融合
4. 可见性过滤在**检索时**做，不是检索完再过滤
   （先检索再过滤会导致"命中 10 条，过滤剩 0 条"，体验极差）

验收：
1. 语义搜索：搜「出差怎么报销」能命中讲「差旅费」的文档
   —— 这是关键词搜不到但语义能搜到的场景，是这个功能的全部意义
2. 关键词搜索：搜精确名词能命中
3. 混合检索结果比单独任一都好（给出三组对比数据）
4. 越权测试：A 搜不到 B 的私有文档

第 3 条要贴真实数据。说"效果更好"不算，要有数字。
```

**为什么 RRF 而不是直接加权求和**：两路检索的分数不在同一个量纲上（BM25 是无界分数，余弦相似度是 -1~1）。RRF 只用排名，不用分数，避免了调权重这个无底洞。

### 提示词 7-C（什么时候才加 ES）

只有满足下面任意一条，才允许引入 Elasticsearch：

- Postgres 全文检索的中文分词效果达不到要求，且试过 pg_jieba/zhparser 仍不行
- 单表行数到千万级，`LIKE`/`tsvector` 查询明显变慢

```
如果决定引入 ES，先回答：
1. 现在慢在哪？给出 EXPLAIN 分析和耗时数字
2. 加了之后正文和索引变成两份，怎么保证同步？失败怎么补偿？
3. ES 挂了，用户看到什么？

⚠️ 命名一致性陷阱：
如果你同时有「块索引」和「文档索引」两个 ES 索引，
**字段命名必须统一**。否则每次排查都要查两次 mapping，
而且会写出查不到结果的查询语句还以为是数据没进去。

推荐全部 snake_case：
  document_id / is_public / author_id / team_id / doc_status
如果两个索引风格不一致（一个 snake 一个 camel），
必须写两个常量把这套差异显式封装，并写进文档。
```

这段最后部分是血泪：两个索引一个 snake_case 一个 camelCase，写排查命令时必然踩一次，而且**查出来恒为 0，会让你以为管线挂了**。

### 提示词 9-C（Agent 化：改写与工具路由）

```

2. 不切题 → 用 LLM 改写检索词 → 再检索一次
3. 二次仍不切题 → 拒答，并说明"未找到相关制度"

- 最多重试一次。无限重试会让用户等很久，且收益递减
- 评估结果要推给前端（data-eval），让用户看到"为什么拒答"
- 评估 reason 用枚举，不要用自由文本：
  ok / retried_ok / empty / retried_empty / irrelevant / retried_irrelevant / error
  （前端要据此显示不同文案，自由文本没法判断）

验收：
1. 一个原本检索不到的模糊问题，改写后能命中 → 回答正确
2. 一个确实不存在的问题，两次都失败 → 拒答，且前端能看到
   是"改写过了仍没找到"而不是"没尝试"
3. 统计：改写带来的命中率提升，给出改造前后的对比数字

第 3 条要真实跑数据，不要估算。
```

## 十、第 7 条竖线：eval（决定这个项目是玩具还是工程）

### 提示词 10-A（先建立基线）

```
建立 AI 效果评测。这一步不是可选项——没有评测，改 prompt 就是盲改。

第一步：金标准数据集
1. 准备 6 份真实制度文档（差旅、安全、采购、考勤等领域）
2. 为每份文档出题，覆盖五类场景：
   - routing：该走知识库还是该说不知道
   - kb-hit：答案在文档里，且能定位到具体文档
   - rewrite：需要改写检索词才能命中
   - kb-empty：文档里确实没有，应该拒答
   - web：需要联网（如果 SCOPE 里有）
3. 每条样本包含：
   question（用户口语化问法，不要照抄文档标题）
   expected.intent
   expected.documents（文档标题子串）
   expected.points（答案应覆盖的要点，用于完整性打分）

规模要求：**至少 60 条**。
9 条上的指标波动全是噪声，判断不出改动好坏。

禁止：
- 不许编造制度条款，每条期望答案都要能在原文找到出处
- 不许把题目出得跟文档标题一样，那样测的是字符串匹配不是问答
```

### 提示词 10-B（指标别贪多）

```
实现评测器。第一版只做 3 个指标：

1. hit_at_5      期望文档是否出现在前 5 条召回里
2. refusal_quality  该拒答时是否拒答，且理由说得对
3. completeness  答案是否覆盖了期望要点（用 LLM 打分，给 rubric）

为什么只做 3 个：指标越多，越多题目"跳过"（返回 null），
反而看不清整体。跑稳了再按需加。

其他要求：
- 每条指标返回 { name, value, comment }
- 不适用的题返回 value: null（跳过），不要返回 0
  —— 0 和"不适用"是两回事
- 支持按 suite 过滤，方便单跑某一类
- 结果能落盘成 JSON，方便前后对比

验收：
1. pnpm eval:rag 能跑完全部 60 条
2. 输出每个指标的平均分和样本数
3. 跑两次，分数差异说明 LLM 的随机性有多大
   （差异超过 5% 的指标，说明样本数还不够）
```

### 提示词 10-C（评测的使用纪律）

```
给项目加一条评测纪律，写进 CLAUDE.md：

1. 改 prompt / 改检索参数 / 换模型之后，**必须跑 eval 并附对比数据**
2. 一次只改一个变量。同时改多个参数说"效果变好了"，无法归因
3. 先跑基线存下来，改完再跑，用 diff 对比
4. eval 不进 CI 的每次 PR：60 条 = 60+ 次 LLM 调用，又慢又贵，
   且 LLM 有随机性，红了不代表改坏了。改成手动触发
5. 指标掉了 5% 以上要停下来查，不要"差不多就行"

把这五条写成 docs/EVAL-POLICY.md。
```

**为什么 eval 不进 CI**：这不是偷懒。LLM 输出有随机性，同样的代码跑两次分数就会有波动；把不确定的东西放进 CI，结果是 CI 经常红，然后所有人都开始忽略 CI。

## 十二、前后端联调

### 12-A 开发期代理

前后端分离开发时，前端通过开发服务器代理转发到后端：

```ts
// vite.config.ts
proxy: {
  '/api': {
    target: 'http://127.0.0.1:3000',
    rewrite: (path) => path.replace(/^\/api/, ''),  // 剥掉 /api 前缀
    timeout: 0,      // 流式对话不能超时
    proxyTimeout: 0,
  },
}
```

**两个必须注意的点**：

- `rewrite` 剥前缀，是因为后端路由没有 `/api` 前缀（`/auth/login` 而不是 `/api/auth/login`）。如果你决定后端加 `/api` 前缀，那这里就不该 rewrite——**前后端必须约定一致**
- `timeout: 0`，流式回答可能持续几十秒，有超时就会被掐断

### 12-B 联调排查提示词

```
前后端联调出问题，按顺序排查，每步给证据，**先不要改代码**：

1. 请求实际打到哪了？打开 Network 看 Request URL 和 Status
2. 后端收到了吗？看后端终端日志
3. 401 → token 带了吗、过期了吗、refresh 生效了吗
4. 流式但前端一次性显示 → 检查响应头 Content-Type，
   以及中间层有没有缓冲（开发代理 / 生产 nginx 都要看）
5. 一直转圈 → useChat 的 status 卡在哪个值

定位到具体环节再改。把证据贴给我。
```

**第 4 条是最典型的"本地好好的、上线就坏"**：开发代理不缓冲，nginx 默认缓冲。

### 12-C 并行开发的前提

前后端可以并行，**前提是 `docs/STREAM-CONTRACT.md` 已定稿**。

```
开两个会话：
- A：只做后端检索与流式编排
- B：只做前端页面与 part 渲染

两边提示词都要写：
「契约见 docs/STREAM-CONTRACT.md，任何偏离契约的改动必须先停下问我。」
```

契约没定就并行，联调时全部返工。

## 十三、部署

### 13-A 先把配置边界搞清楚

先纠正一个高频误解：**前端没有运行时环境变量**。

前端构建工具的环境变量是**构建期字符串替换**，打包完就焊死在 JS 里了。运行时改 `.env` 对前端无效。

| 配置 | 放哪 | 说明 |
|---|---|---|
| 前端 API 地址 | 构建阶段，或干脆不配 | 不配就用相对路径 `/api`，由 nginx 反代，**推荐** |
| 后端全部配置 | 服务器上的 `backend.env`，`env_file` 注入 | **绝不打进镜像** |
| 中间件密码 | compose 同目录的 `.env`，被 `${VAR}` 插值 | compose 只认这个目录的 `.env` |
| LLM / 邮件 / JWT 密钥 | `backend.env` | 最高敏感度，`chmod 600` |

```
/opt/app/
├── docker-compose.prod.yml
├── .env            # 中间件密码，chmod 600
├── backend.env     # 后端全部配置，chmod 600，永不进 git
└── volumes/
```

### 13-B 应用服务进 compose

开发用的 compose 通常只起中间件。上生产要追加应用服务：

```yaml
  backend:
    build: { context: ., dockerfile: Dockerfile }
    restart: unless-stopped
    env_file: ./backend.env
    environment:
      # 容器内用服务名互访，覆盖 backend.env 里的 127.0.0.1
      POSTGRES_HOST: postgres
      REDIS_HOST: redis
      ES_NODE: http://es:9200
      HOSTNAME: 0.0.0.0        # ← 关键，否则容器外访问不到
    depends_on:
      postgres: { condition: service_healthy }
      redis:    { condition: service_healthy }
    healthcheck:
      # 用公开的健康检查接口，不要用需要鉴权的
      test: ["CMD", "node", "-e", "fetch('http://127.0.0.1:3000/').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"]
      interval: 15s
      start_period: 40s

  frontend:
    build: { context: ../frontend, dockerfile: Dockerfile }
    ports: ["80:80"]
    depends_on:
      backend: { condition: service_healthy }
```

三个坑：

1. **`HOSTNAME: 0.0.0.0`** —— Nest 在容器里默认可能绑 localhost，容器外连不上。这是"容器起来了但打不开"的头号原因
2. **健康检查用公开接口** —— 带鉴权的接口会被健康检查请求打成 401，容器永远 unhealthy
3. **`depends_on` 配 `condition: service_healthy`** —— 只写 `depends_on` 是"启动顺序"不是"就绪顺序"

### 13-C nginx 反代（流式的生死线）

```nginx
server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;

    # SPA 路由 fallback，否则刷新子页面 404
    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://backend:3000/;   # 尾斜杠 = 剥掉 /api
        proxy_http_version 1.1;
        proxy_set_header Connection '';

        # 流式必须的三条
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 300s;

        client_max_body_size 50m;
    }
}
```

**两个会导致"上线就坏"的点**：

- `proxy_pass` 的**尾斜杠**：不带尾斜杠，`/api/auth/login` 会原样转成 `http://backend:3000/api/auth/login`，后端没这个前缀 → **所有请求 404**
- `proxy_buffering off`：不关，nginx 会把 SSE 攒在缓冲区，表现为**生产环境一次性刷出整段回答**，而本地开发一切正常

### 13-D 部署提示词

```
把项目部署到 Linux 服务器。

请完成：
1. 后端 Dockerfile（多阶段构建，生产镜像不含 devDependencies）
2. 前端 Dockerfile + nginx.conf
3. docker-compose.prod.yml
4. backend.env.example（值全部用明显假值，如 YOUR_KEY_HERE）
5. docs/DEPLOY.md：首次部署 / 升级 / 回滚三个流程
```

## 十五、这套方法的总账

到这里你已经有了一个能跑的完整系统。回头看，决定成败的从来不是提示词写得多漂亮，而是四件事：

1. **范围先定死**（`SCOPE.md`），不做清单比做清单长
2. **数据模型先于代码**，且先证明 Postgres 够用
3. **一轮一条竖线**，每条都有能跑的命令 + 反向测试
4. **没跑通就说没跑通**，禁止"应该可以"

### 提示词自检清单

每段提示词粘出去前，自查五项：

- [ ] **范围**：说清楚改哪几个文件，以及**明确不改什么**
- [ ] **事实**：涉及状态机/权限/数据结构的，把已确定的约束复述在提示词里，别让它猜
- [ ] **验收**：至少一条能跑的命令 + 期望输出，必须包含一条**反向测试**
- [ ] **禁止项**：能否吞异常、能否改断言、能否一次改多个参数
- [ ] **停止点**：做完这一步停下，不要顺手继续

反向测试的例子：
- `已归档文档再归档应返回 400`
- `草稿即使 isPublic=true 别人也读不到`
- `知识库没有的问题必须拒答，且不调 LLM`
- `并发三个 401 请求，refresh 只出现一次`

**能通过反向测试的实现才是真的实现了，而不是只走了 happy path。**

## 十七、如果只能记住三句话

1. **一次会话一条竖线，跑不通不进下一条。**
2. **验收必须有反向测试**——只能通过正向测试的实现，往往只是"能跑"。
3. **AI 会把没验证的说成验证过**，所以每次都要它贴命令输出，而不是贴总结。
